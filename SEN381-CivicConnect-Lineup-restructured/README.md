# CivicConnect

CivicConnect is a citizen-facing service-request platform being built as the SEN381 integrated project. Citizens submit
requests, staff progress them through a controlled lifecycle (Submitted → Accepted/Rejected → Resolved), and every
status change is committed with an auditable history entry.

## Current implementation status (M2)

| Requirement | Status |
|---|---|
| FR-13 (lifecycle transitions) | In Development |
| FR-05 (status/history commit) | In Development |
| FR-08 (requester feedback) | In Development |
| FR-03, FR-12 | In Development |
| All other FRs/NFRs | Not Yet Implemented |

The full, authoritative status for every requirement is the RTM (`rtm.json` / `RTM.html`), not this table — this table is
a summary only.

## What's implemented right now

A single executable reference slice: authorised staff can accept a submitted request, and the status/history change is
committed atomically and readable back by the owning citizen. This proves the core lifecycle, integrity and access-control
decisions end-to-end; it is **not** a complete application (no web UI, no authentication, no deployment).

## Prerequisites

- Python 3.12.x (verified against 3.12.14; see `evidence/verification.txt`)
- No external packages — the project deliberately uses only the Python standard library (see PED Section 48.2)

## Setup / run

```bash
git clone https://github.com/VoidMeBro/SEN381-CivicConnect-Lineup.git
cd SEN381-CivicConnect-Lineup
python product/demo.py          # run the demo lifecycle path
python -m unittest discover -s tests -v   # run all 35 tests
```

## Repository structure

```
product/
  schema.sql       SQLite schema (accounts, requests, lifecycle_events, categories)
  lifecycle.py     RequestLifecycleCoordinator, LifecyclePolicy, SqliteLifecycleStore
  demo.py          Runnable CLI demo
tests/
  test_lifecycle.py     Lifecycle/persistence/access tests
  test_traceability.py  Traceability-tool tests (imports traceability.py at repo root)
evidence/
  verification.txt      Recorded local test-run output
  product_demo.json      Recorded demo output
traceability.py    Local RTM/change-control validator tool (NFR-06 / ADR-M1-01)
rtm.json           Canonical, editable Requirements Traceability Matrix
baseline_m1.json   Approved M1 baseline snapshot used by traceability.py
change_register.json  Controlled-change records checked by traceability.py
source_manifest.json  Source hash manifest for tamper checks
docs/
  PED/             Project Engineering Document (controlled, versioned)
  decisions/       ADRs (ADRs.md)
  governance/      GitHub governance record
  requirements/    RTM.html — a static rendered view only; rtm.json above is canonical
  baselines/       Signed-off baseline snapshots, including M1_original_v0.11.docx (the
                   byte-for-byte preserved M1 source; its SHA-256 is checked against
                   source_manifest.json — do not edit this file)
.github/workflows/
  tests.yml        Runs the test suite on every PR to main
```

`traceability.py` and its JSON files (`rtm.json`, `baseline_m1.json`, `change_register.json`, `source_manifest.json`)
are kept together at the repo root deliberately: the tool resolves them by relative path
(`Path(__file__).parent`), and `tests/test_traceability.py` imports the module assuming it sits at the repo root.
Moving any of these into `docs/` breaks both the CLI and the tests.

This maps directly onto the modular-monolith architecture in PED Section 41: `product/lifecycle.py` is the
logical-module boundary, not a separately deployed service.

## Database / migrations

The schema is created by `product/schema.sql` and applied by `SqliteLifecycleStore.initialise()`. There is currently one
schema revision — no migration tooling is needed yet (see PED Section 45.2 for the portability rationale).

## Interfaces

There is currently no external API. Internal calls go through an in-process application contract
(`RequestLifecycleCoordinator.transition(...)`, `.history(...)`) as decided in ADR-M2-03 / PED Section 47. A REST
boundary will only be introduced once a genuine external client exists.

## Configuration / environment

No environment variables or secrets are required for the current reference slice — the demo creates and discards its own
temporary SQLite database. See PED Section 49.2 for the direction planned once real configuration (e.g. a persistent DB
path) is introduced.

## Testing

Run locally with:
```bash
python -m unittest discover -s tests -v
```
The same command runs automatically in CI (`.github/workflows/tests.yml`) on every pull request into `main`. Current
evidence: 35 tests passing (20 lifecycle/persistence/access + 15 traceability) — see `evidence/verification.txt`.

## Known limitations / TODOs

- No authentication — the service accepts an already-authenticated actor ID from its caller.
- No web UI, network API, or deployment yet.
- SQLite is appropriate for the current reference slice only; see PED Section 49.3 for the deferred decision on a
  server-based database.
- Full CI/CD (build → deploy) is deliberately not yet implemented (PED Section 50.3).
